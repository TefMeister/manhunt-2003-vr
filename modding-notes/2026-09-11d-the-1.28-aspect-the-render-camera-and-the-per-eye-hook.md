## 1. (a) Who writes the aspect `[0x007A164C]` and view window `[0x007A1650]`: nobody `[inferred-static]`

- **Both are initialised data.** `1.28f` (`0A D7 A3 3F`) and `0.7f` (`33 33 33 3F`) sit in
  `manhunt.exe`'s `.data` on disk. No instruction in `.text` writes either address, neither by
  absolute address nor as TheCamera+`0x6A0`/`+0x6A4`; every `+0x6A0` store is in character code.
- **They are read exactly once each**, at `0x005932BE` / `0x005932C4`, inside the camera creator
  `0x00593210` (GTA3's `CameraCreate(w, h, zbuf)` shape). The creator calls `0x00593390`, which
  calls **`RwCameraSetViewWindow` (`0x00626360`)** with **(0.7, 0.7 / 1.28) = (0.7, 0.546875)**. It
  also writes the derived FOVs in degrees to `0x007A1654` / `0x007A1658`.
- **The world camera is made once per level.** StartupLevel `0x004D8520` → `0x00473900` →
  `0x00473990` → `CameraCreate` at **`0x004739A0`**, with the game's mode width and height
  (`[[0x00736DB8]+4]`, `+8`). The result is stored to **`[0x00715B94]`**, and the zoom `[0x00715C94]`
  is set to 1.0.
- **Per frame**, `0x00475BC0` (called only from the render, at `0x00475F6E`):
  - reads the camera's current view window back into `[0x00715C98]/[0x00715C9C]`;
  - adds the game's own widescreen-option offsets `[0x00715CDC]/[0x00715CE0]` (0 / 0, or +0.04 / −0.06
    when set by `0x00476AA0`);
  - divides by the zoom and sets the result;
  - `0x0047624C` puts the saved value back after the frame.
  - **Fallback:** if the stored x exceeds 1.9, it resets from IMMEDIATES:
    `0x3F333333` (0.7) at `0x00475BFB` and `0x3F0C0000` (0.546875) at `0x00475C05`. That is the same
    1.28 pair again. It can happen: the camera code at `0x0058F8A3` sets x = 2.0 in one special mode.
- **What 1.28 is:** a baked constant, not derived from any screen size. The binary cannot say why:
  it equals 640/500, and also 4:3 × 0.96. The fallback pair 0.7 / 0.546875 is 1.28 exactly.
- **The live projection matches the camera exactly:** m00 = 1/0.7 = 1.4286 and m11 = 1/0.546875 =
  1.8286 are the logged values `[verified-live 2026-09-10]`.
- **The cleanest single place is the creator call at `0x004739A0`.** It is the only point where the
  game hands over the real width and height. Setting the two globals there (plus the one fallback
  immediate) makes every later per-frame step inherit the right aspect. The one-float-in-`.data`
  alternative has to guess the size and misses the fallback.

**Built, opt-in (`src/aspect.c`), `[compile-verified 2026-09-11]`.**

How it works:
- With an empty `manhunt_vr_fix_aspect` beside the exe, the call at `0x004739A0`
  (`E8 6B F8 11 00`) is re-targeted to a wrapper, from the game's own w, h:
  1. it sets `[0x007A164C] = w/h` and `[0x007A1650] = 0.546875 × w/h`;
  2. it patches the fallback x immediate at `0x00475BFB`;
  3. it calls the original creator unchanged.
- This is "Hor+": the vertical view stays 57.3°, and the horizontal becomes 2·atan(0.546875·w/h),
  which is 88.4° at 16:9 (the stock horizontal is 70.0°).
- It refuses w < h, with a log line. It logs `ASPECT: world camera WxH -> aspect …` at each level
  start.

## 2. (b) `[0x00715B94]` IS the world render camera, and the chain to `D3DTS_VIEW` `[inferred-static]`

1. The app-state render dispatcher `0x004D7EB0` does `push [0x00715B94]; call 0x00475EA0` (at
   `0x004D7EC7`). The in-game render's only argument is that camera (`ebp` throughout).
2. `0x00475890(cam)`: `RwCameraClear` (`0x00626290`), then **`RwCameraBeginUpdate(cam)`** at
   `0x00475969`. `0x006260E0` is `jmp [cam+0x18]`; `EndUpdate` `0x006260D0` is `jmp [cam+0x1C]`.
3. `cam+0x18` is the D3D8 driver's camera begin-update **`0x00641CE0`**. It is put in the device
   function table at `0x00640449`, standard RenderWare. It:
   1. stores the current camera to `[0x00828470]`;
   2. gets the frame `[cam+4]` → **`RwFrameGetLTM` (`0x006184C0`)**;
   3. runs **`RwMatrixInvert` (`0x00619880`)**;
   4. **negates the X column** (handedness);
   5. calls **`_rwD3D8SetTransform(D3DTS_VIEW = 2, m)`** at `0x00641D99`.
4. It then builds the projection from the same camera and calls
   `_rwD3D8SetTransform(D3DTS_PROJECTION = 3)` at `0x00641E37`. The inputs are:
   - `1/viewWindow` (`+0x70/+0x74`);
   - the view offset (`+0x78/+0x7C`), which gives the off-axis terms at `0x00641D9E`–`0x00641DD3`;
   - near/far (`+0x80/+0x84`);
   - the type (`+0x14`).
5. `_rwD3D8SetTransform` **`0x00643330`** compares the 16 dwords with a per-state cache and
   **returns without calling D3D when unchanged**. Otherwise it calls
   `IDirect3DDevice8::SetTransform` (vtable `+0x94`, device `[0x00824448]`). That is exactly what
   `proxy.c`'s `Hooked_SetTransform` logs as `VIEW #n` / `PROJECTION #n`.
   - ⚠️ Because of the cache, `VIEW` counts drop whenever the camera holds still.
   - That cache may be why the 2026-08-26 hook saw "no SetTransform in gameplay". The other
     candidate is that the run never left the intro movie. Both are `[hypothesis]`.

**What is not proven.** The frontend overlay camera `[0x007CF078]` is made by the same creator with
the same 1.28 view window, so the PROJECTION match alone does not separate the two cameras. VIEW
does.

**Cheap live proof:** compare one logged `VIEW` with `POS` in the same second.
- The camera position from VIEW is −Rᵀ·t, after undoing the X-column negation.
- It should equal `POS camera eng=`, since `POS` reads the same `[0x00715B94]` frame `+0x40`.

## 3. (c) The per-eye hook point `[inferred-static]`, where to call is `[hypothesis]`

**What one frame of `0x00475EA0(cam)` does, in order:**

| Step | Address | What it is |
| --- | --- | --- |
| 1 | `0x0058F5E0` | Camera update (game camera → RwCamera frame). Also runs at `0x00475F4A` and `0x00476262`. |
| 2 | `0x00475F06` | White-noise gate: if the flag is set, only the noise overlay draws, then return. |
| 3 | `0x00618FF0` | Frame matrix check. |
| 4 | `0x00475BC0` | **View window set, once per frame.** |
| 5 | `0x00475F9D` … `0x0047609D` | **Pass 1, the world and characters:** `0x00475890` Clear+Begin, world `0x004759B0`, then the entity and effect calls, then `EndUpdate` at `0x0047609D`. |
| 6 | `0x004760D3` … `0x0047612F` | **Pass 2:** Begin, then `0x005C3510` on `0x007BA930` and further effect / overlay calls, then End. |
| 7 | `0x00476149` … `0x00476228` | **Pass 3, HUD and 2D:** Begin, then `0x005F31E0` / `0x005EF900` / `0x00489EE0`, then End. |
| 8 | `0x00476241` | `0x005934B0(cam)`: show the raster (Present). Then the view-window restore at `0x0047624C`. |

**So:**
- **There is one world camera and no per-camera loop.** The world is drawn once per frame, in
  pass 1.
- **`0x00475EA0` is one level too high to call twice.** It would run the camera update and Present
  twice, and draw the HUD twice.
- **Per-eye setup point:** the call at **`0x00475F6E`** (→ `0x00475BC0`). It runs exactly once per
  frame, the camera frame is final, and the next instruction path is Clear+BeginUpdate. Put the
  eye's view window / view offset / frame translation there.
- **Stereo means re-running pass 1**, and probably pass 2. HUD pass 3 runs once (or once per eye
  onto a quad). The natural re-entry is to hook the `EndUpdate` at `0x0047609D`: after eye L,
  switch camera state and render target and jump back to `0x00475F9D`; after eye R, restore and
  continue.
  - ⚠️ **Vet before re-running:** pass 1 also calls `0x005CB260`/`0x005CB3C0` (on `0x007C5604`),
    `0x0043B140`, `0x006218F0`, `0x00477C50`, `0x004753F0`, `0x00444930`, `0x004F9EF0` and
    `0x00478CB0`. Any that advances game state (particles, timers) would run twice per frame. That
    these are render-only is `[hypothesis]`; check each.
- **Per-eye tools already in the binary:**
  - `RwCameraSetViewWindow` `0x00626360` (per-eye tangents);
  - **`RwCameraSetViewOffset` `0x006260F0`**, RenderWare's off-axis term, already folded into the
    projection by `0x00641CE0`. The game never uses it, so the view offset is 0 today;
  - translate the camera frame `[cam+4]` (matrix `+0x10`, position `+0x40`) along its right vector
    by ±IPD/2, then mark it dirty (`0x00618440`, which the two setters also call).
  - Set these **before** `BeginUpdate`, so the frustum used for world-sector culling is the eye's.
- **Why engine-level beats D3D replay:** RenderWare's skinned characters carry their matrices in
  vertex-shader constants (the proxy's `SetVertexShaderConstant` hook). A D3D-level draw replay
  would have to patch those per eye as well. Re-running pass 1 with a changed camera gets them
  right for free.
- Respect the white-noise gate (step 2): when it is set, there is nothing to stereo.
